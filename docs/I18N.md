# Localization

Recipe Lab uses Android's standard resource system. English is the complete default
catalog in `res/values/strings.xml`; locale-specific files may override only the
strings they translate. Android falls back to the default resource for anything a
locale does not provide.

The app does not implement a language picker, call `Locale.setDefault`, alter
camera language settings, or cache localized strings. A recreated Activity/View
reads the current Android resource configuration.

## Architecture

`UiText` is part of the Android presentation layer. It references `R.string`,
`R.array` and `R.plurals` directly, so missing resource names are build-time
errors instead of runtime string lookups. Core camera classes remain Android-free:
`Params`, `Recipes`, `Favourites`, `DevTools`, `Keys` and `KeyProbe`.

`Keys` exposes named semantic hint ids rather than English words. `Legend`
asks `UiText` to render those actions for the current locale. Camera setting IDs,
CameraEx keys, stored bytes, key gestures and diagnostic file formats stay
locale-neutral.

Recipe identity and display names are deliberately separate:

- `Recipes.Recipe.name` stays the canonical persistence/diagnostic identity.
- `UiText` maps each canonical group/recipe name to a compile-time `R.string` display resource and verifies that
  the mapping still matches the core tables when the class loads.
- group/brand display names use independent `group_*` resources.
- recipe display names use independent `recipe_*` resources.

A locale can therefore translate a brand, an individual recipe, both, or neither
without changing favourites or any camera setting.

## Adding a translation

Add `res/values-<language>[-r<region>]/strings.xml`. The default catalog must stay
complete, but a locale catalog may be partial. Do not repeat resources marked
`translatable="false"`.

Translate complete messages rather than concatenating translated fragments.
Positional format arguments such as `%1$s` and `%2$d` may be reordered but must
keep their index and type. Arrays are positional enum tables: if a locale overrides
one, it must provide the complete array in the same order.

Product names may stay unchanged where that is the local convention. Brand and
recipe display names are separate resources specifically so Japanese, Traditional
Chinese, Simplified Chinese and other locales can use their own established names.

When a recipe is added, add its English `recipe_*` resource and the matching
`UiText.RECIPE_NAMES` entry next to the same canonical name. The core recipe table
itself remains Android-free and favourites continue to use the canonical name.

## Tests

```
./tools/test-i18n.sh
./tools/test.sh
./build.sh
```

`tools/test-i18n.sh` is intentionally small: it checks XML/resource types and
format placeholders, then runs the Unicode wrapping/ellipsizing tests. It does not
try to parse Java source or duplicate aapt/javac. The normal test job covers the
camera-free core; the build job is the authoritative Android resource/Java/NDK/APK
compile check.

Camera font rendering and final Canvas layout still require a real-device check.

## Camera acceptance checklist

- Test English and each added locale selected in the camera menu.
- Reopen Recipe Lab after changing language and verify no stale text.
- Verify TextView and Canvas CJK glyphs, prompts, menus, browser columns and hints.
- Verify long translated brand/recipe names fit or ellipsize correctly.
- Confirm favourites survive language changes because canonical recipe identity did
  not change.
- Confirm reset and RAW/RAW+JPEG behavior are unchanged.
- Compare CameraEx/settings writes against the same upstream build.
- Power-cycle after picking a recipe and verify the stored look still survives.

Localization does not change image processing, Picture Profile behavior, RAW
behavior, settings IDs, native code, permissions, signing, versioning or firmware.


## Small-APK conventions

Recipe Lab keeps the new localization action identities as named primitive constants rather than Java enums.
The app is unusually small and does not run an R8 shrinker, so the localization layer avoids adding enum/runtime
machinery solely for display semantics. Existing camera protocol representations remain unchanged unless a symbolic
name is required by the localization boundary.
